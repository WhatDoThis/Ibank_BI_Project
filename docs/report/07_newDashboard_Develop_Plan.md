# NewDashboard 범용 대시보드 개발 계획

**문서 목적**: 테이블 스키마에 맞춰 화면이 자동 구성되는 **범용 대시보드** 제작 가능 여부 검토 및 Phase별 개발 계획 정리.  
**패키지명**: `newDashboard` (신규). 기존 대시보드 패키지에서 UI 제거 대상만 뺀 파일을 복사한 뒤 수정하는 방식.

---

## 1. 요구사항 정리

| # | 요지 | 상세 |
|---|------|------|
| 1 | **집계 기준·컬럼 선택·정렬** | 현재: 지정 컬럼 하드코딩 → 해당 요소용 템플릿으로 집계/정렬/컬럼 선택 구성. **목표**: 테이블 로드 시 해당 테이블의 **집계 기준 후보 = 실수형(real/double precision/numeric 등 연속형)이 아닌 컬럼**(날짜, 문자, 정수형 포함)을 리스트로 두고, 이에 따라 컬럼 선택창·정렬 기준이 동적으로 업데이트. |
| 2 | **주요 지표·목표 설정** | 1번에 맞게 구성. 목표 설정은 **숫자형(정수·실수) 데이터 타입** 컬럼에 대해서만 구성(SUM 등으로 목표 대비 비교). |
| 3 | **주요 지표 섹션** | 1·2에 따라 해당 컬럼 요소를 **자동 탐색**해 구성. 가능하면 **모든 숫자형 컬럼**에 대해 KPI 카드 구성. 단, 컬럼 수가 많을 경우 표시 개수 제한·스크롤·접기 등 UI 정책 필요. |
| 4 | **제외 섹션** | **채널별 분석**, **기준별 발송 현황**, **위젯 생성** 섹션은 해당 페이지에 없음. **위젯 생성 (beta)** 는 유지. |
| 5 | **집계 테이블** | 선택된 테이블 스키마에 맞게 동적 구성. |
| 6 | **위젯 생성 (beta)** | 선택형 데이터(디멘션/메트릭 등)가 **선택된 테이블**에 맞게 구성. |

**정리**: 모든 기능이 **선택된 테이블 스키마**에 따라 동적으로 구성되는 **범용 대시보드** 페이지 제작 가능 여부 검토 및 계획 수립.

## 2. 현행 구조 요약 (검토 기준)

### 2.1 백엔드 (dashboard_service, dashboard2 라우터)

- **테이블 목록**: `get_aggregatable_tables()` → `DASHBOARD_REQUIRED_COLUMNS`에 정의된 컬럼·타입을 **모두** 만족하는 테이블만 반환.
- **필수 컬럼**: `delivery_date`, `campaign_id`, `campaign_label`, `workflow_id`, `workflow_label`, `delivery_channel`, `total_count`, `success_count`, `failed_count`, `open_count`, `click_count` 등 **고정**.
- **집계 데이터**: `_build_group_by_clause(group_by)` → `campaign` / `date` / `workflow` / `channel` 4개 축 고정. SELECT/GROUP BY 절이 해당 컬럼명에 하드코딩.
- **KPI**: `_calculate_kpi()` → `campaign_count`, `workflow_count`, `channel_count`, `total_send`, `total_success`, … 등 **고정 키**와 고정 수식(success_rate, open_rate, click_rate 등).
- **필터 옵션**: `get_filter_options()` → `campaigns` / `workflows` / `channels` 전용 쿼리(컬럼명 고정).
- **차트 데이터**: `get_chart_data()` → `CHART_DIMENSION_KEYS`, `CHART_METRIC_KEYS` 고정.

### 2.2 프론트엔드 (dashboard2 패키지)

- **집계 기준**: `Dashboard2Header` 등에서 `groupBy: { campaign, date, workflow, channel }` 고정.
- **디멘션/메트릭**: `DIMENSION_FIELDS`, `METRIC_FIELDS` 상수로 라벨·키 고정.
- **KPI**: `KPICards2` → `ALL_KPI_KEYS`, `CARD_CONFIG` 고정 (캠페인 수, 워크플로우 수, 발송, 성공률 등).
- **목표**: `TargetContextSection` → 지표 키가 고정; 목표값은 실수형 대응만 하면 됨.
- **집계 테이블**: `AggregatedDataTable2` → 컬럼 정의가 `delivery_date`, `campaign_label`, `workflow_label`, `channel_name`, `total_count`, `success_count`, … 등 고정.
- **위젯 (beta)**: `EChartsChart` → dimension/metric 키가 `METRIC_FIELDS`/`DIMENSION_FIELDS` 기반 고정.

### 2.3 기존 공용 유틸 (참고)

- **widgetboard/utils/dataUtils.js**: `describe-table` 응답 컬럼으로 `isNumericType`, `isDimensionType` 판별 후 `pickDimensionAndMetric`, `aggregateForChart` 등 제공. **범용 대시보드에서 재사용/확장 가능**.
- **타입 필드 통일**: describe-table 응답의 컬럼 타입 필드명(`type` vs `data_type`)이 백엔드·프론트 간 동일한지 확인 필요. 범용 API에서 스키마를 내려줄 때 **차원/메트릭 분류**를 백엔드에서 수행하면 프론트는 그대로 사용해 일관성 유지 가능.

### 2.4 범용화 시 유의할 점 (개발 리스크)

- **정수형 컬럼의 이중 성격**: 정수형이어도 `id`, `user_id` 등 **고유값이 많은 컬럼**은 “집계 기준(차원)”으로 쓰면 카디널리티가 폭발해 집계 테이블·필터 옵션이 비대해질 수 있음. “차원 후보에서 제외” 또는 “차원으로 허용하되 필터 옵션 상한(예: 상위 1000건)” 등 정책을 문서/구현에 명시할 것.
- **동적 SQL과 보안**: 집계 기준·메트릭·필터에 **컬럼명을 그대로 넣으면 SQL injection** 위험이 있음. 백엔드에서는 반드시 **describe/스키마 조회 결과와 대조한 화이트리스트**로만 컬럼명을 허용하고, 테이블명은 기존 `validate_table_name` 등 검증을 그대로 적용할 것.

## 3. 범용 대시보드 가능성 검토

### 3.1 결론: **구현 가능**

- **집계 기준 = 비실수형(차원형) 컬럼**: 스키마에서 **실수형(real, double precision, numeric 등)** 이 아닌 컬럼을 집계 기준 후보로 둠. **날짜/타임스탬프, 문자, 정수형(integer, bigint 등)** 은 모두 차원 후보에 포함. 기존 “캠페인/일자/워크플로우/채널”을 **테이블별 동적 리스트**로 대체 가능.
- **주요 지표**: 숫자형 컬럼은 SUM/COUNT 등으로 KPI화 가능; 비율 지표는 “분자/분모 컬럼”이 있는 경우에만 도입하거나, 1차적으로는 **원시 숫자 컬럼 합계 + 선택적 비율**만 지원해도 요구사항 충족 가능.
- **목표 설정**: 숫자형(정수·실수) 컬럼만 목표값 입력 대상으로 두면 됨.
- **집계 테이블**: 선택된 집계 기준(디멘션) + 선택된 메트릭(숫자 컬럼)으로 SELECT/GROUP BY를 동적 생성하면 됨.
- **위젯 생성 (beta)**: 이미 `dataUtils`처럼 describe-table 기반 dimension/metric 후보가 있으므로, **선택된 테이블의 describe 결과**를 넘겨 동일한 방식으로 선택형 데이터 구성 가능.

### 3.2 전제 조건

- **테이블 목록**: “범용” 시 **모든 allowed_tables**를 노출하거나, “날짜(또는 timestamp) 컬럼 1개 이상 + 숫자형 컬럼 1개 이상” 등 **최소 스키마 조건**을 만족하는 테이블만 노출하는 정책 선택 필요.
- **날짜 필터**: 집계 기준에 날짜/타임스탬프 타입 컬럼이 있으면 기간 필터로 사용; **날짜 컬럼이 여러 개일 때**는 “기간 필터에 쓸 컬럼”을 사용자 선택 또는 첫 번째 날짜 컬럼 자동 지정 등 정책 필요. 없으면 기간 필터 비활성화 또는 “전체 기간”만 허용.
- **필터 옵션**: “캠페인/워크플로우/채널” 대신 **선택된 테이블의 비실수형 컬럼별**로 `DISTINCT` 값 목록을 내려주는 **범용 필터 API**가 필요. **카디널리티가 매우 높은 컬럼**(예: user_id 수만 건)은 DISTINCT 상한(예: 1000건) 또는 검색/페이지네이션으로 제한해야 UI·성능 문제를 막을 수 있음.
- **컬럼 표시명(라벨)**: 범용 화면에서는 컬럼명(영문/스네이크)만으로는 가독성이 떨어질 수 있음. 1차는 **컬럼명 그대로 표시**, 추후 DB comment 또는 메타(컬럼별 한글 라벨)를 내려받아 표시하는 옵션을 두면 범용성과 UX를 함께 만족시키기 쉬움.

## 5. 패키지·파일 전략

- **패키지**: `Frontend/react-app/src/packages/newDashboard` 신규 생성.
- **초기 구성**: 사용자가 **폴더 생성 및 기존 대시보드 파일 복사**를 수행. **dashboard2 기준 복사 권장**(비교 모드, 디멘션별/요약, periodCompare 등이 이미 반영됨). 이후 에이전트가 **파일 내용 변경·파일 정리** 수행.
- **복사 시 제외**: 채널별 분석, 기준별 발송 현황, (일반) 위젯 생성 관련 컴포넌트는 복사하지 않거나 복사 후 제거.  
  - 예: `ChannelDonutCharts2`, `AggregatedBarChart2`(기준별 발송) 등은 범용 버전으로 대체하거나 제외.
- **유지 후 수정**: `KPICards` → 스키마 기반 KPI 목록, `AggregatedDataTable` → 스키마 기반 컬럼, `TargetContextSection` → 숫자형 컬럼만 목표, `EChartsChart`(위젯 beta) → 테이블 기반 dimension/metric 선택.

### Phase 1: 백엔드 범용 API

**목표**: 테이블 스키마 기반으로 테이블 목록·필터 옵션·집계 데이터·차트 데이터를 반환하는 API 구성.

| 작업 | 내용 |
|------|------|
| **1.1 테이블 목록** | `get_aggregatable_tables()` 대체 또는 신규: **allowed_tables** 중 “날짜/타임스탬프 컬럼 1개 이상 + 숫자형 컬럼 1개 이상” 등 최소 조건 만족 테이블만 반환. 또는 일단 모든 allowed_tables 노출 후 describe 기반 필터링은 프론트에서 처리(선택). |
| **1.2 describe-table 활용** | 기존 `POST /api/describe-table` 유지. newDashboard 전용 **스키마 메타 API**가 필요하면 `GET /api/new-dashboard/table-schema/{table_id}` 형태로 “컬럼 목록 + data_type + 차원/메트릭 분류” 반환 검토. |
| **1.3 범용 필터 옵션** | `get_filter_options(table_id, campaigns, workflows, channels)` 대신 **비실수형 컬럼별** `DISTINCT` 값 목록 반환. 예: `GET /api/new-dashboard/filter-options/{table_id}?dimension_columns=col1,col2` 또는 스키마에서 차원 컬럼 자동 판별 후 컬럼별 옵션 반환. |
| **1.4 범용 집계 데이터** | 요청에 `table_id`, `date_range`, `group_by`(동적 컬럼 키 목록), **필터**(컬럼별 값 목록), 선택적 `date_column` 등. 응답: 선택된 디멘션 컬럼 + 숫자 컬럼 SUM/COUNT 등. `_build_group_by_clause`를 “컬럼명 리스트” 기반 동적 생성으로 교체. **날짜 컬럼이 없으면** `date_range` 무시·전체 기간으로 조회하거나, 조회 자체를 비활성화하는 정책 중 하나를 선택. |
| **1.5 범용 KPI** | 숫자형 컬럼에 대해 SUM (및 필요 시 COUNT DISTINCT) 반환. 비율 지표는 “분자/분모 컬럼” 지정이 있으면 계산, 없으면 1차적으로 생략 또는 옵션. |
| **1.6 범용 차트 데이터** | dimension/metric을 **컬럼명**으로 받아 해당 테이블에 맞게 GROUP BY / SUM 동적 쿼리. 기존 `CHART_DIMENSION_KEYS`, `CHART_METRIC_KEYS` 제거. |

**보안·구현 원칙**: 동적 쿼리에서 사용하는 **모든 컬럼명·테이블명**은 반드시 **화이트리스트 검증** 후 사용. 테이블명은 `validate_table_name`, 컬럼명은 해당 테이블의 describe/스키마 API 결과에 존재하는 이름만 허용. 사용자 입력을 이스케이프만 하고 넣지 말 것.
**산출물**: newDashboard 전용 라우터(예: `/api/new-dashboard/*`) 및 서비스 레이어(또는 dashboard_service 확장).

### Phase 2: 프론트 – 테이블 선택·스키마 로드·헤더(집계 기준·필터)

**목표**: 테이블 선택 시 describe 기반으로 집계 기준 리스트·필터·정렬 기준을 화면에 반영.

| 작업 | 내용 |
|------|------|
| **2.1 테이블 선택** | newDashboard 테이블 목록 API 연동. 선택 시 `describe-table`(또는 Phase 1 스키마 API) 호출. |
| **2.2 차원/메트릭 분류** | `dataUtils.isNumericType`, `isDimensionType` 등 활용해 컬럼을 “집계 기준(차원)” / “메트릭(숫자)” 로 분류. 날짜 컬럼은 기간 필터·집계 기준 후보로 사용. |
| **2.3 헤더 – 집계 기준** | `groupBy`를 `{ campaign, date, workflow, channel }` 대신 **테이블의 비실수형 컬럼 목록**으로 체크박스/토글 구성. 선택된 컬럼만 GROUP BY에 참여. |
| **2.4 헤더 – 필터** | “캠페인/워크플로우/채널” 대신 **차원 컬럼별** 필터(멀티 셀렉트). 필터 옵션은 Phase 1 범용 필터 API로 조회. |
| **2.5 기간 필터** | 날짜/타임스탬프 타입 컬럼이 있으면 해당 컬럼으로 기간 필터 적용; **여러 개일 때**는 “기간 필터에 쓸 컬럼”을 사용자 선택 또는 첫 번째 날짜 컬럼 자동 지정. 없으면 “기간 없음” 또는 비활성화. |
| **2.6 테이블 전환 시 state** | 테이블을 바꾸면 **집계 기준·필터·정렬·목표** 등 이전 테이블 기준 state는 초기화. 새 테이블 스키마에 맞는 기본값(예: 날짜 컬럼 1개만 groupBy 등)으로 재설정해 범용성과 혼선 방지. |

**집계 기준 0개 선택**: 사용자가 집계 기준을 하나도 선택하지 않은 경우 “전체 합계 1행” 또는 “집계 기준을 1개 이상 선택하세요” 안내 등 동작을 한 가지로 정의할 것.
**산출물**: NewDashboardPage 상단 테이블 선택 + 집계 기준 + 필터 UI 동작.

### Phase 3: 주요 지표(KPI)·목표 설정·집계 테이블

**목표**: 스키마 기반 KPI 카드, 실수형 컬럼만 목표 설정, 집계 테이블 컬럼 동적 구성.

| 작업 | 내용 |
|------|------|
| **3.1 KPI 카드** | Phase 1 KPI 응답 키를 그대로 표시. 카드 구성은 **숫자형 컬럼별** 자동 생성(라벨은 컬럼명 또는 메타에서 가져오기). 표시/숨김 선택(localStorage)은 기존처럼 유지. |
| **3.2 목표 설정** | `TargetContextSection`: 목표 입력 대상 지표를 **숫자형 컬럼(또는 KPI 키)** 만 노출. 기간 유형·목표값 저장/불러오기는 기존과 동일. |
| **3.3 집계 테이블** | 선택된 집계 기준(차원) + 선택된 메트릭(숫자 컬럼)으로 테이블 컬럼 정의 동적 생성. 정렬·필터 툴바는 “현재 선택된 컬럼”에 맞게 동작. 비교 모드(디멘션별/요약)가 있으면 동일 로직을 범용 컬럼에 적용. |

**KPI 개수 정책**: 숫자형 컬럼이 많은 테이블은 KPI 카드가 과도하게 늘어남. **최대 표시 개수(예: 12개)** 제한 후 나머지는 “더 보기”/스크롤/접기, 또는 **표시할 메트릭 선택 UI**로 제한하는 것을 권장(요구사항 3 반영).
**숫자형이지만 “개수” 지표**: `id`처럼 고유값 개수를 세는 것이 의미 있는 컬럼은 SUM 대신 **COUNT(DISTINCT col)** 로 KPI 노출하는 옵션을 두면 범용성 향상. 1차는 SUM만 지원하고, 필요 시 확장.
**산출물**: 주요 지표 섹션, 목표·컨텍스트 섹션, 집계 테이블이 모두 “선택된 테이블”에 맞게 동작.

### Phase 4: 위젯 생성 (beta)

**목표**: EChartsChart(또는 동일 역할 컴포넌트)에서 dimension/metric을 **선택된 테이블의 describe 결과**로 채우기.

| 작업 | 내용 |
|------|------|
| **4.1 선택형 데이터** | 위젯 설정의 디멘션/메트릭 셀렉트 옵션을 **현재 테이블의 차원 컬럼 목록** / **메트릭 컬럼 목록**으로 구성. dataUtils 분류 결과 또는 Phase 1 스키마 API 활용. |
| **4.2 차트 데이터 요청** | 범용 차트 API에 `table_id`, `dimension`, `metric`, 기간·필터 전달. 응답을 그대로 차트에 바인딩. |
| **4.3 비교 모드** | 비교 모드(기준/비교 기간)가 있으면 기존처럼 기준 기간·비교 기간 각각 요청 후 차트에 반영. |

**차트 가독성**: 디멘션 카디널리티가 큰 컬럼(예: 수백 개 레이블)을 선택하면 X축이 겹쳐 가독성이 떨어짐. **상위 N건(예: 20)만 표시 + “기타”로 합산** 옵션을 API 또는 프론트에서 적용하면 범용 테이블에서도 쓸 만한 차트를 유지할 수 있음.
**산출물**: 위젯 생성 (beta)가 테이블 변경 시 자동으로 해당 테이블의 차원/메트릭만 노출하고 차트 생성 가능.

### Phase 5: 비교 모드·기간 표시·정리

**목표**: 일/주/월/연 비교, 기간 라벨, 불필요 코드 제거 및 라우트·네비 연동.

| 작업 | 내용 |
|------|------|
| **5.1 비교 모드** | 기존 periodCompare 유틸 활용. 집계 데이터/차트/KPI 요청 시 “기준 기간 / 비교 기간” 각각 파라미터로 전달. 백엔드가 두 기간 데이터를 반환하거나, 프론트에서 두 번 호출 후 병합. |
| **5.2 기간 표시** | 주요 지표·집계 테이블 상단 등에 PeriodLabel(기준/비교 기간) 표시. |
| **5.3 라우트·네비** | `/new-dashboard`(또는 정한 경로) 및 상단 네비에 “범용 대시보드” 등 메뉴 추가. |
| **5.4 정리** | 사용하지 않는 컴포넌트 import/파일 삭제, 린트/문서 정리. |
| **5.5 진입점·라우트** | `newDashboard/index.jsx`에서 페이지 컴포넌트 export. 앱 라우터에 `/new-dashboard`(또는 `/ibank-bi/new-dashboard`) 등록 및 상단 네비 링크 추가. |

**localStorage 정책**: 목표 저장(`*_targets`), KPI 표시/숨김(`*_kpi_visible`) 등은 **테이블별로 키를 나눌지**(예: `newDashboard_targets_${table_id}`) **단일 키에 table_id 포함 객체로 저장할지** 사전에 정하면 테이블 전환 시 목표/설정이 꼬이지 않음.
**산출물**: 범용 대시보드 페이지 완료, 배포 가능 상태.

## 8. 추가 제안 사항

| # | 제안 | 비고 |
|---|------|------|
| 1 | **스키마 메타 API 일원화** | describe-table만 쓰면 프론트에서 타입별 분류를 반복 구현하게 됨. **`GET /api/new-dashboard/table-schema/{table_id}`** 로 “컬럼 목록 + data_type + dimension/metric 분류 + (옵션) 표시명”을 한 번에 내려주면 프론트는 그대로 바인딩만 하면 되어 범용성·일관성이 좋음. |
| 2 | **차원 컬럼 제외 옵션** | 카디널리티가 매우 높은 컬럼(id, user_id 등)을 “집계 기준 후보에서 제외”하는 정책을 스키마 API 또는 설정에서 지원하면, 기본 목록만으로도 안전한 UI를 만들 수 있음. (예: 컬럼 메타에 `exclude_from_group_by: true` 또는 네이밍 규칙으로 자동 제외) |
| 3 | **집계 테이블 내보내기** | 범용 대시보드 결과를 CSV/엑셀 등으로 내보내는 기능을 Phase 5 이후에 추가하면, “어떤 테이블이든 보고서처럼 내보내기” 요구에 대응하기 쉬움. |
| 4 | **테스트용 테이블** | 개발·검수 시 **스키마가 서로 다른 테이블 2개 이상**(예: 기존 대시보드용 테이블 + 컬럼 수/타입이 다른 간단 테이블)으로 전환하며 E2E 테스트하면, 하드코딩 잔존 여부와 범용 동작을 빠르게 검증할 수 있음. |
| 5 | **비율 지표 확장** | 1차는 “원시 숫자 컬럼 SUM”만 지원하고, 추후 “분자 컬럼 / 분모 컬럼”을 사용자가 지정해 비율(%)을 만드는 UI/API를 넣으면, 성공률·오픈률 같은 지표를 범용 테이블에서도 구성 가능. |
