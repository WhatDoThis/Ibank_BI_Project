## 전제 및 제안 사항

### 1. 목표(Target) 저장 구조 제안

요청하신 컬럼: `flag / 지표 / 년 / 월 / 기간(년.월~년.월) / 목표`

**제안: 저장 단위를 하나의 객체 배열로 두고, 기간은 계산 가능 필드로 두기**

| 필드 | 타입 | 설명 |
|------|------|------|
| `periodType` | `'year' \| 'month' \| 'range'` | 목표 단위(연/월/기간) |
| `metric` | string | 지표 키. 예: `total_send`, `total_success`, `success_rate`, `open_rate`, `click_count`, `click_rate` (API·KPI와 동일 키 권장) |
| `year` | number | 연도 (필수) |
| `month` | number \| null | 월. `periodType === 'month'` 일 때만 사용(1~12), 나머지는 null |
| `rangeStart` | string \| null | `periodType === 'range'` 일 때만. `'YYYY-MM'` |
| `rangeEnd` | string \| null | `periodType === 'range'` 일 때만. `'YYYY-MM'` |
| `targetValue` | number | 목표값 (실수 포함 가능) |

**기간 라벨(표시용)** 은 프론트에서 계산:
- `year` → `"YYYY.01~YYYY.12"`
- `month` → `"YYYY.MM~YYYY.MM"`
- `range` → `"rangeStart~rangeEnd"` (예: `2026.01~2026.03`)

이렇게 하면 나중에 DB 테이블로 옮길 때도 `period_type`, `metric`, `year`, `month`, `range_start`, `range_end`, `target_value` 컬럼으로 매핑하기 쉽고, 중복 저장을 줄일 수 있습니다.

### 2. 목표 저장소: HttpOnly 쿠키 vs localStorage

#### 2.1 용량 검토 (목표지수는 쿠키로 충분한지)

목표 1건을 JSON으로 직렬화한 예:

```json
{"periodType":"month","metric":"total_send","year":2026,"month":5,"rangeStart":null,"rangeEnd":null,"targetValue":10000000}
```

- **1건당 약 100~120 바이트** (키 이름을 짧게 하면 80바이트 대로도 가능).
- **쿠키 상한**: 도메인당 쿠키 1개 기준 **약 4KB(4096바이트)**.
- **건수 추정**: 4096 ÷ 110 ≈ **약 37건**. 짧은 키 사용 시 **50건 이상**도 가능.
- **실사용**: 목표지수는 “지표×기간” 단위로 저장(예: 2026년 발송수, 2026년 5월 오픈률, 2026.Q1 성공수 등). 사용자당 **10~30건** 수준이면 충분하고, 50건을 넘기는 경우는 드뭅니다.

**결론: 목표지수 규모에서는 4KB 제한이 문제되지 않으며, HttpOnly 쿠키만으로도 충분히 유용합니다.**

#### 2.2 HttpOnly 쿠키 vs localStorage 비교

| 항목 | HttpOnly 쿠키 | localStorage |
|------|----------------|--------------|
| **용량** | 약 4KB/쿠키 | 보통 5~10MB/도메인 |
| **목표지수 적합성** | ✅ 10~50건 수준이면 여유 있음 | ✅ 용량 문제 없음 |
| **XSS 노출** | ✅ JS로 읽기 불가 → 탈취·변조 어려움 | ❌ 같은 오리진의 JS가 읽기·쓰기 가능 |
| **구현** | 백엔드 API 필요(GET/POST targets, Set-Cookie/파싱) | 프론트만으로 저장·로드 가능 |
| **요청 시 전송** | 매 요청에 쿠키 포함(헤더 수십~수백 바이트) | 전송 없음 |
| **만료/도메인** | 만료일·Path·SameSite 설정 가능 | 영구(사용자 삭제 시까지) |

#### 2.3 권장

- **보안(XSS)을 우선**하면 → **HttpOnly 쿠키**를 쓰는 것이 좋고, 목표지수 용량은 위 검토대로 **충분히 유용**합니다.
- **백엔드 수정 없이 빠르게 검증**하려면 → **localStorage**로 1차 구현 후, Phase 1 후반 또는 추후에 **GET/POST targets API + HttpOnly 쿠키**로 옮기는 방식도 가능합니다. (저장 형식은 1장 구조를 그대로 쓰면 이전이 쉽습니다.)

**적용 결정**: 추후 테이블(DB)에서 목표를 읽어오면 저장소는 교체되므로 **DEV용으로 localStorage** 사용. Phase 1에서는 백엔드 targets API 없이 프론트에서 localStorage로 저장·로드. (기존 문장: 플랜 기본안은 **HttpOnly 쿠키**로 두고 “테스트만 먼저 할 때는 localStorage 허용”을 선택 사항으로 두는 것을 권장합니다.

#### 2.4 HttpOnly 쿠키 저장 시 기술 유의사항

- HttpOnly 쿠키는 **클라이언트(JavaScript)에서 설정·읽기 불가**이므로, **백엔드**에서 Set-Cookie로 저장하고, 조회 시 요청에 실린 쿠키를 백엔드가 읽어 JSON으로 내려주는 방식이 필요합니다.
- Phase 1 제안: **백엔드 목표 전용 API 2개**  
  - `GET /api/dashboard/targets` → 쿠키에서 목표 배열 읽어 `{ targets: [...] }` 반환  
  - `POST /api/dashboard/targets` → body `{ targets: [...] }` 받아 직렬화 후 HttpOnly 쿠키로 저장  
- 쿠키 크기는 위 용량 검토대로 **목표지수 규모에서는 문제 없음**. 다만 다른 용도로 같은 쿠키를 쓸 계획이 있다면, 전체 크기가 4KB를 넘지 않도록 항목 수 또는 페이로드 크기를 관리하는 것이 안전합니다.

### 3. 대시보드2 레이아웃 제안 (개선안 반영 후)

1. **상단**: 필터(테이블·기간·집계 기준·캠페인/워크플로우/채널) — Phase 0에서 복사한 헤더

## Phase 1: 목표·컨텍스트 섹션 + 목표 저장/로드 (DEV: localStorage)

**목표**: “목표·컨텍스트” 표시 섹션 추가, 기간 유형(연/월/기간) + 지표 선택 후 목표값 입력·저장, DEV용 localStorage로 보관·로드(추후 테이블/API 전환 가능).

### 1.1 목표 데이터 구조 (프론트·백 공통)

위 **1. 목표 저장 구조 제안** 사용. 한 건 예시:

```json
{
  "periodType": "month",
  "metric": "total_send",
  "year": 2026,
  "month": 5,
  "rangeStart": null,
  "rangeEnd": null,
  "targetValue": 10000000
}
```

지표 키는 KPI와 맞추기: `total_send`, `total_success`, `total_failed`, `total_open`, `total_click`, `success_rate`, `open_rate`, `click_rate`, `campaign_count` 등.

### 1.2 백엔드 (목표 쿠키 API)

- **GET /api/dashboard/targets**  
  - 요청에 실린 쿠키(예: `dashboard_targets`)에서 JSON 배열 파싱 후 `{ targets: [...] }` 반환. 없으면 `{ targets: [] }`.
- **POST /api/dashboard/targets**  
  - body: `{ targets: [ { periodType, metric, year, month?, rangeStart?, rangeEnd?, targetValue }, ... ] }`  
  - 유효성 검사 후 JSON 직렬화, **HttpOnly, Secure, SameSite=Lax, Path=/** 쿠키로 저장(이름 예: `dashboard_targets`).  
  - 응답: `{ ok: true }` 또는 에러.

쿠키 크기 제한을 고려해 항목 수 상한(예: 50건)을 두는 것을 권장.

### 1.3 프론트: 목표·컨텍스트 섹션 UI

- **위치**: 필터(헤더) 바로 아래, “주요 지표” 섹션 위.
- **왼쪽**: (Phase 2에서 보강) “리포트 기간: …” 등 컨텍스트 표시.
- **오른쪽**:  
  1. **기간 유형** 셀렉트: `년도` | `월` | `기간(년.월~년.월)`  
  2. **지표** 셀렉트: 발송수(total_send), 성공수(total_success), 오픈률(open_rate), 클릭수(click_count), 클릭률(click_rate), 성공률(success_rate), 오픈수(total_open), 실패수(total_failed), 캠페인수(campaign_count) 등  
  3. **년도** 입력: 숫자(예: 2026). `월` 선택 시 **월** 입력(1~12). `기간` 선택 시 **시작(YYYY-MM)** / **종료(YYYY-MM)** 입력  
  4. **목표값** 입력: 실수만 허용 (유효성 검사)  
  5. **저장** 버튼: 위 값을 1건으로 추가해 `POST /api/dashboard/targets` 호출(기존 targets 배열에 추가한 새 배열 전송). 성공 시 목록 갱신·표시.

저장 시 기존 `targets`를 GET으로 불러온 뒤, 동일 `periodType + metric + year + month + rangeStart + rangeEnd` 조합이 있으면 **덮어쓰기**, 없으면 **추가** 후 POST하는 방식 권장.

### 1.4 저장된 목표 표시

- 같은 섹션 또는 “주요 지표” 위에 “저장된 목표” 리스트(테이블 또는 카드)로 표시: 기간 라벨, 지표명, 목표값. (삭제 버튼은 선택.)

### 1.5 검수

- 연/월/기간 각각 선택 후 목표 입력·저장 → 새로고침 후에도 목표가 유지되는지(쿠키에서 로드) 확인.
- 브라우저 개발자 도구에서 해당 쿠키가 HttpOnly로 설정되어 있는지 확인.

## Phase 2: 기간 표시 명시화 + Executive Summary

- **리포트 기간 라벨**: “리포트 기간: YYYY-MM-DD ~ YYYY-MM-DD”를 목표·컨텍스트 섹션 왼쪽 또는 상단에 표시. `filters.date_range` 포맷.
- **Executive Summary**(선택): 대표 KPI 1~2개 + 한 줄 요약 문구 입력 필드(나중에 DB/API로 저장 가능). Phase 2에서는 로컬 state만 써도 됨.

## Phase 3: 지표 정의 툴팁

- KPI 카드·집계 테이블 헤더에 “?” 또는 아이콘 추가, 호버/클릭 시 해당 지표의 **정의·계산식** 툴팁 표시.
- `KPICards2.jsx`의 카드 설정에 `definition` 문자열 추가, `AggregatedDataTable2.jsx` 헤더에도 동일 방식 적용.

## Phase 4: 신호등 표시 (목표 대비 달성 여부)

- Phase 1에서 로드한 `targets`와 현재 필터 기간·집계 결과 KPI를 매칭(periodType/year/month 또는 range에 따라).
- 매칭된 목표가 있는 KPI에 대해 **실적/목표 비율** 계산, 구간(예: ≥100% 초록, 80~100% 노랑, &lt;80% 빨강)에 따라 카드 테두리·뱃지·아이콘 색상 적용. “달성”/“주의”/“미달” 텍스트 병기 권장.

## Phase 5·6 (선택)

- **Phase 5**: 변동성·인사이트용 코멘트 영역(텍스트 입력·표시). 저장은 로컬 state 또는 별도 API로 추후 확장.
- **Phase 6**: 액션 플랜·다음 조치 블록(텍스트 입력·표시).

## 진행 방식

- **Phase 0** 완료 후 여기서 한 번 끊고, 동작 확인·적용 여부 결정.
