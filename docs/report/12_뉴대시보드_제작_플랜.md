# 12. 뉴대시보드 제작 플랜

**문서 목적**: 기존 대시보드 API를 재활용한 **일간/주간/월간** 현황판 스타일의 New Dashboard 페이지를 체계적으로 제작하기 위한 Phase별 플랜. 헤더 우측에 **일간·주간·월간** 토글이 있으며, period에 따라 조회 기간·날짜 이동 단위가 달라진다. 서브에이전트 병렬 작업 가능하도록 단위·의존성·대상 파일을 명시한다.

**데이터 소스**: `ibank_test_data` 스키마의 **ibank_1** 테이블. API에서는 `table_id = "ibank_1"` 로 전달하며, 스키마는 `Backend/api_server/db.get_table_schema()`(config 기반)에서 결정된다. `get_aggregatable_tables()`가 반환하는 목록에 `ibank_1`이 포함되어야 하며, 해당 테이블은 `DASHBOARD_REQUIRED_COLUMNS`(delivery_date, campaign_id, campaign_label, workflow_id, workflow_label, delivery_channel, total_count, success_count, failed_count, open_count, click_count)를 모두 만족해야 한다.

**참고 문서**: 07_newDashboard_Develop_Plan.md(범용 대시보드 검토), 사용자 제공 가이드(Phase별 Cursor 프롬프트).

**일간/주간/월간 반영**: 프로토타입 이미지의 헤더 우측 **일간·주간·월간** 토글을 반영한 사양이다. 기존 Phase 가이드에서 **Phase 1, 2a(2-1), 3, 4(4-1 SummaryHeader), 5(CSS)** 를 사용자 제공의 "Phase 1 교체", "Phase 2-1 교체", "Phase 3+4-1 교체", "Phase 5 CSS 추가" 프롬프트로 **교체**하여 적용하면 된다. 나머지 Phase(4-2~4-6, 6, 7)는 그대로 사용.

## 2. Phase 1: 백엔드 — 기간별 요약 엔드포인트 (일간/주간/월간)

### 2.1 목표

기존 `dashboard_service.get_dashboard_data`, `dashboard_service.get_chart_data`, `dashboard_service.get_aggregatable_tables`를 **그대로 호출**하고, `/api/new-dashboard/*` 경로로만 분리한다. **summary** 엔드포인트는 (1) `period`에 따라 `date_range`를 계산하는 헬퍼, (2) **이전 기간 대비 증감률**을 위해 직전 동일 기간을 한 번 더 조회하는 로직을 **라우터 내부**에 추가한다. **trend-multi**는 일자별 복수 메트릭을 한 번에 반환하는 새 엔드포인트(라우터에서 직접 쿼리 또는 서비스 확장). 기존 `dashboard_service`의 기존 함수 시그니처는 수정하지 않는다.

### 2.2 생성 파일: `Backend/api_server/routers/new_dashboard.py`

- **prefix**: `/api/new-dashboard`, **tags**: `["new-dashboard"]`
- **헬퍼**: `_calc_date_range(target_date: str, period: str)`  
  - `daily`: 해당 일자 하루 → `[target_date, target_date]`  
  - `weekly`: 해당 일자가 속한 주 (월요일~일요일) → `[start, end]` (월요일 시작, weekday 0=월)  
  - `monthly`: 해당 일자가 속한 월 (1일~말일) → `[start, end]` (calendar.monthrange 활용)
- **엔드포인트**:
  - `GET /api/new-dashboard/summary?table_id=&target_date=&period=daily|weekly|monthly`  
    - `target_date` 미지정 시 오늘. `period` 기본값 **`daily`**(첫 진입 시 일간 현황), 유효하지 않으면 `daily`로 폴백.  
    - `date_range = _calc_date_range(target_date, period)` 계산 후 `get_dashboard_data(req)` 호출.  
    - **`group_by`는 반드시 `{"campaign": True, "date": True, "workflow": True, "channel": True}` 로 고정.** (CampaignRankTable "워크플로우별" 탭에서 프론트 reduce 재집계 시 workflow_id·workflow_label이 필요하므로 aggregated_data에 workflow 정보가 포함되어야 함. `workflow: False`면 집계 결과에 워크플로우가 나오지 않음.)  
    - 반환: `{ kpi, aggregated_data, filter_applied, period, date_range_actual }` (프론트 표시용으로 실제 조회 기간 포함)
  - `GET /api/new-dashboard/trend?table_id=&end_date=&days=30&metric=success_count`  
    - (기존과 동일) `end_date` 미지정 시 오늘. `start_dt = end_dt - (days-1)일`, `get_chart_data(req)` 호출.  
    - 반환: `{ rows: [ { name, value, delivery_date? }, ... ] }`
  - `GET /api/new-dashboard/tables`  
    - `get_aggregatable_tables()` 호출 후 `{ tables: [ { id, name } ] }` 형태로 반환 (id/name 모두 테이블명, 예: `ibank_1`)

- **2.2.1 이전 기간 대비 증감률 (KPI 카드용)**  
  summary 엔드포인트는 **현재 기간 KPI 조회 후, 직전 동일 기간도 자동 조회**하여 증감률을 계산한다.  
  - daily → 전일 대비, weekly → 전주 대비, monthly → 전월 대비.  
  - **헬퍼 `_calc_previous_range(date_range, period)`** 추가:  
    - daily: 전일 `[D-1, D-1]`  
    - weekly: 전주 `[W-1 월요일, W-1 일요일]`  
    - monthly: 전월 `[M-1 1일, M-1 말일]` (calendar.monthrange 활용)  
  - **헬퍼 `_calc_change_pct(current, previous)`**: `previous`가 0이거나 없으면 `None`, 아니면 `round((current - previous) / previous * 100, 2)`.  
  - **동작**: 현재 기간으로 `get_dashboard_data` 호출 → 이전 기간 `date_range_prev = _calc_previous_range(date_range_actual, period)`로 한 번 더 `get_dashboard_data` 호출 → 현재/이전 KPI의 total_send, total_success, total_open, total_click로 증감률 계산.  
  - **응답 확장**: `kpi` 내에 `send_change_pct`, `success_change_pct`, `open_change_pct`, `click_change_pct` 포함 (비교 불가 시 `None`). 선택적으로 `previous_kpi`(이전 기간 KPI 전체)를 응답에 포함해 프론트에서 추가 활용 가능.

- **2.2.2 복수 메트릭 추이 (추이 그래프용)**  
  - `GET /api/new-dashboard/trend-multi?table_id=&end_date=&days=30`  
  - 일자별로 **total_count, success_count, open_count, click_count**를 한 번에 반환. `GROUP BY delivery_date`로 단일 쿼리. (기존 `get_chart_data`를 4회 호출하지 않고, **라우터에서 db 모듈을 사용해 직접 쿼리**.)  
  - **필수 import**: `from Backend.api_server import db`. 테이블명 검증·스키마: `db.validate_table_name(table_id)`, `db.get_table_schema()`, `db.get_db_connection()`.  
  - **SQL 패턴 (pseudo-code)**: table = `"{schema}"."{table_name}"` (validate_table_name, get_table_schema 사용). WHERE `delivery_date BETWEEN %s AND %s` (start_date, end_date). SELECT `delivery_date::text AS date`, `COALESCE(SUM(total_count),0)::bigint AS total_count`, `COALESCE(SUM(success_count),0)::bigint AS success_count`, `COALESCE(SUM(open_count),0)::bigint AS open_count`, `COALESCE(SUM(click_count),0)::bigint AS click_count` FROM {table} WHERE ... GROUP BY delivery_date ORDER BY delivery_date ASC.  
  - **응답**: `{ rows: [ { date: "2024-10-01", total_count: 100, success_count: 90, open_count: 50, click_count: 10 }, ... ] }`  
  - 전환(conversion) 컬럼은 현재 스키마에 없으면 제외하거나 0으로 둠.

- **에러 처리**: `ValueError` → 400, 기타 → 500, `JSONResponse`로 `{ "error": str(e) }` 반환.
- **파일 상단 주석**: 프로젝트 규칙에 따라 모듈 설명·엔드포인트·`_calc_date_range`·의존성 기재.

### 2.3 수정 파일: `Backend/api_server/main.py`

## 3. Phase 2a: API 클라이언트 확장

### 3.1 목표

`Frontend/react-app/src/shared/api/client.js`에 New Dashboard 전용 함수 **4개**(getNewDashboardTables, getNewDashboardSummary, getNewDashboardTrend, getNewDashboardTrendMulti)를 **기존 패턴(getDashboardData 등)과 동일 스타일**로 추가. 기존 함수는 수정하지 않는다.

### 3.2 추가 함수

- `getNewDashboardTables()`  
  - `GET ${getApiBase()}/api/new-dashboard/tables`  
  - 반환: `{ tables: [ { id, name } ] }`
- `getNewDashboardSummary(tableId, targetDate = null, period = 'daily')`  
  - `GET .../api/new-dashboard/summary?table_id=...&period=...`  
  - `targetDate` 있으면 쿼리 파라미터 `target_date` 추가. `period`는 `'daily' | 'weekly' | 'monthly'`, **기본값 `daily`**(페이지 첫 진입 시 오늘 일간 현황).  
  - 반환: `{ kpi, aggregated_data, filter_applied, period, date_range_actual }` (kpi 내 `send_change_pct`, `success_change_pct`, `open_change_pct`, `click_change_pct` 포함 가능)
- `getNewDashboardTrend(tableId, { endDate = null, days = 30, metric = 'success_count' } = {})`  
  - `GET .../api/new-dashboard/trend?table_id=...&days=...&metric=...`  
  - `endDate` 있으면 `end_date` 쿼리 파라미터 추가
- `getNewDashboardTrendMulti(tableId, { endDate = null, days = 30 } = {})`  
  - `GET .../api/new-dashboard/trend-multi?table_id=...&end_date=...&days=...`  
  - 반환: `{ rows: [ { date, total_count, success_count, open_count, click_count }, ... ] }` (추이 그래프 멀티 라인용)

- **공통**: `fetch` 사용 시 `res.ok` 아니면 `throw new Error(...)` (에러 메시지는 상태 코드 등 활용). 응답 `res.json()` 반환.
- **base URL**: `shared/config/api.js`의 `getApiBase()` 사용 (기존 client.js와 동일).

### 3.3 체크리스트 (Phase 2a)

- [ ] getNewDashboardSummary 기본 period `daily`

## 5. Phase 3: 메인 페이지 — 레이아웃 및 데이터 로딩

### 5.1 목표

NewDashboardPage에서 **실제 API를 호출**해 **일간/주간/월간** 현황을 표시. 테이블은 `getNewDashboardTables()`로 목록 조회 후 **첫 번째 테이블을 기본 선택**(예: ibank_1이 목록 첫 번째면 자동 선택). 날짜는 `YYYY-MM-DD`, 기본값 **오늘**. **period** 상태로 일간(daily)·주간(weekly)·월간(monthly) 전환. **period 기본값은 `daily`**(페이지 첫 진입 시 오늘 일간 현황).

### 5.2 데이터 흐름

1. 마운트 시 `getNewDashboardTables()` → `tables` 상태 저장, `tableId`가 비어 있으면 `tables[0].id`로 설정.
2. `tableId`·`targetDate`·`period` 확정 시 **loadData**에서는 **summary + trend-multi만 호출** (trend 단일 메트릭 API는 호출하지 않음):  
   - `getNewDashboardSummary(tableId, targetDate, period)` → `summaryData` (kpi, aggregated_data, period, date_range_actual; kpi에 증감률 포함)  
   - **`getNewDashboardTrendMulti(tableId, { endDate: targetDate, days: 30 })`** → `trendMultiData` (rows: [{ date, total_count, success_count, open_count, click_count }]).  
   - `Promise.all([ getNewDashboardSummary(...), getNewDashboardTrendMulti(...) ])` 로 한 번에 요청.  
   - (getNewDashboardTrend 단일 메트릭은 API만 두고, 초기 로딩·추이 그래프에는 사용하지 않음. 향후 확장용.)
3. 상태: `tableId`, `targetDate`, **`period`** (`'daily' | 'weekly' | 'monthly'`, **기본값 `'daily'`**), `tables`, `summaryData`, **`trendMultiData`** (trendData 제거 — 추이 그래프는 trendMultiData만 사용), `loading`, `error`.
4. 날짜 이동(**moveDate**): **period에 따라 이동 단위 변경** — daily: ±1일, weekly: ±7일, monthly: ±1개월. 변경 시 summary·**trend-multi** API 재호출.
5. `dateRangeActual`: 서버 응답의 `date_range_actual`을 SummaryHeader에 전달해 주간/월간일 때 기간 표시(예: 2024.10.14 ~ 10.20, 2024.10).

### 5.3 레이아웃 (위→아래)

- **SummaryHeader**: 테이블 셀렉트, 날짜 표시(period별 형식) 및 ◀/▶, **일간/주간/월간 토글**, 새로고침 버튼.
- **에러 메시지**: `error`가 있으면 표시.
- **캠페인 요약**: KPISummaryCards(kpi, distribution, changePcts). 증감(▲▼%) 표시, **2행 카드 안에 미니 도넛 인라인** (이미지 기준으로 카드 내장 형태).
- **채널별 분포**: **NewDashboardPage 레이아웃에서는 별도 "채널별 분포" 섹션을 두지 않음.** 채널 도넛은 KPISummaryCards 2행 카드 안 미니 도넛으로 통합. ChannelDonutSection 컴포넌트는 **파일은 생성하되 Phase 4에서는 구현하지 않고 빈 껍데기만 유지** (향후 별도 채널 분석 페이지 확장 시 활용).
- **전체 추이 그래프**: TrendLineChart(data=trendMultiData?.rows). 5개 라인(발송요청/성공/오픈/클릭/전환), 우측 범례+최신값.
- **전체 발송 분석**: FunnelSection(kpi). 5단계(발송요청→성공→오픈→클릭→**전환**, 전환 없으면 0 또는 N/A 표시).

- **동작** (향후 구현 시): send·success 기준 도넛 가로 배치. recharts PieChart innerRadius/outerRadius.

### 6.5 TrendLineChart

- **Props**: **data** — **trend-multi** API 응답의 `rows`: `[{ date, total_count, success_count, open_count, click_count }, ...]`. (기존 trend 단일 메트릭 rows가 아닌 trendMulti 사용.)
- **동작**:

### 6.6 FunnelSection

- **Props**: kpi.
- **동작**: **이미지 영역 F(전체 발송 분석)** 만 담당. 발송 요청(total_send) → 발송 성공(total_success) → 오픈(total_open) → 클릭(total_click) → **전환**(현재 스키마에 전환 컬럼 없으면 **0 또는 N/A**로 표시) 가로 막대 또는 퍼널 5단계. 우측 "현재 가이드": 성공률/오픈률/클릭률에 따른 신호등(✅/🔶/🔴) 기준(예: 성공률 90% 이상 ✅, 80~90% 🔶, 80% 미만 🔴 등). **이미지에 "전환" 단계가 있으므로** 전환 바를 0 또는 N/A로라도 표시해 레이아웃을 맞춘다.  
- **이미지 영역 H(하단 퍼널도)**: FunnelSection과 별도. **별도 컴포넌트 파일은 생성하지 않음.** FunnelSection 하단 또는 동일 페이지 하단에 `{/* TODO: 하단 퍼널도 (플레이스홀더) */}` 주석·빈 영역만 둠. (§4.2 생성 파일 목록에 BottomFunnelPlaceholder 미포함)

### 6.7 CampaignRankTable

    - **전체**: 기존 aggregated_data 그대로 사용.  
    - **캠페인별**: campaign_id(및 campaign_label) 기준으로 프론트에서 **reduce로 재집계**(날짜·채널 무시, total_count/success_count 등 SUM).

  - 테이블: success_count DESC 정렬, 컬럼 순위, 캠페인명(또는 워크플로우명), 채널, 발송요청, 발송성공, 성공률, 오픈, 오픈률, 클릭, 클릭률. 페이지네이션 5건씩. 채널명은 channel_name 또는 CHANNEL_MAP[channel_code].

## 10. 최종 데이터 흐름 (period 반영)

```
[프론트] period='weekly', targetDate='2024-10-15'
    ↓
[GET] /api/new-dashboard/summary?table_id=xxx&target_date=2024-10-15&period=weekly
    ↓
[백엔드] _calc_date_range('2024-10-15', 'weekly')
    → date_range = ['2024-10-14', '2024-10-20']  (월~일)
    ↓
[기존 서비스] dashboard_service.get_dashboard_data(date_range=['2024-10-14','2024-10-20'])
    ↓
[응답] { kpi, aggregated_data, filter_applied, period: 'weekly', date_range_actual: ['2024-10-14','2024-10-20'] }
```

- **period 토글만 바꿔도** 같은 API에서 일간/주간/월간 데이터가 자동으로 range 계산되어 반환된다. 기존 `dashboard_service` 로직은 수정하지 않는다.

## 11. 의존성 및 순서 요약

```
Phase 1 (백엔드 라우터)
    ↓
Phase 2a (API 클라이언트) ← Phase 1 완료 후

    ↓
```
